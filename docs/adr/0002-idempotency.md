# ADR 0002: Idempotent transfers

Status: Proposed · Date: 2026-11-15

## Context

A client sends `POST /transfers`, the server posts the journal entry, and the response is lost: a timeout, a dropped
mobile connection, a proxy that gives up. The client can't tell whether the money moved. It retries, and the same
money moves twice. Retries come from many places: HTTP clients and mobile apps retry on timeout automatically, and a
double click sends two requests.

The server can't solve this alone by comparing requests. Two identical requests can both be real: a user may pay a
friend 10.00 EUR twice on purpose. Only the client knows whether a request is a retry, so the client has to say so.

Today the posting service writes each entry in one transaction to a single PostgreSQL database. No endpoint exists
yet; `POST /transfers` is the first. Amounts arrive as JSON strings and are parsed into `Money` (ADR 4).

## Decision

1. **Key:** every request that moves money (`POST /transfers`, later top-ups) must send an `Idempotency-Key` header
   holding a UUID generated by the client, one per operation. A missing or malformed key gets `400`.
2. **Scope:** a key belongs to one user. The stored key is `(user_id, key)`, so two users can't collide or see each
   other's responses.
3. **Storage:** a new `idempotency_keys` table in the same database: `user_id`, `key`, `request_hash`,
   `response_status`, `response_body` (JSONB), `entry_id`, `created_at`. Primary key `(user_id, key)`. The exact
   schema ships in the V5 migration.
4. **Fingerprint:** `request_hash` is a SHA-256 of the parsed request (method, path, accounts, `Money` amount,
   description), not of the raw bytes. `"10.0"` and `"10.00"` become the same `Money`, so they get the same hash.
5. **Same transaction:** the service inserts the key row first (`INSERT ... ON CONFLICT DO NOTHING`), posts the entry,
   stores the response on the key row, and commits all of it together. Either the entry and the key both exist, or
   neither does.
6. **Retries:**
    - New key: process the request.
    - Same key, same hash, already committed: return the stored status and body unchanged, with the header
      `Idempotent-Replayed: true`. Nothing is posted again.
    - Same key, different hash: `422`. The client reused a key for a different operation, which is a client bug.
    - Same key while the first request is still running: the second insert waits on the primary key until the first
      transaction ends, then replays its response (or, if the first rolled back, processes the request). If the wait
      passes `lock_timeout`, the answer is `409` and the client retries later.
7. **Failures are not stored:** a request that fails (unknown account, unbalanced entry, insufficient funds) rolls
   back, and its key row rolls back with it. A retry runs again and may succeed if the state changed. Money still
   moves at most once.
8. **Retention:** keys are kept for 24 hours, the same window as Stripe. A scheduled job deletes older rows. After
   that, the same key starts a new operation.
9. **Who and why:** the initiator (`created_by`) and the kind of entry (`entry_type`) live on the journal entry, not
   on a transfer record, because top-ups, reversals and system entries are not transfers. The key row points to
   the entry through `entry_id`.

## Consequences

**Gains**

- A lost response can be retried safely: the client gets the original answer, and money moves at most once.
- No separate store can drift from the ledger: the key and the entry commit or roll back together.
- Concurrent duplicates are serialized by the database's primary key, with no extra locking code.
- Clients get clear signals: replay header, `422` for a misused key, `409` for "still running, try later".
- The pattern follows Stripe and the IETF `Idempotency-Key` draft, so client developers already know it.

**Costs**

- One more table, a stored response per request, and a cleanup job.
- The check must run inside the posting transaction, in the service layer. A servlet filter would run in its own
  transaction and lose the atomicity.
- The fingerprint must be updated whenever the request shape changes, or real retries start getting `422`.
- A retry after 24 hours is treated as a new operation. Clients must not retry that late without checking the
  transaction history first.
- Failed requests are not replayed, unlike Stripe, which caches errors once execution starts. A retry can succeed
  where the first attempt failed. This is accepted because the money still moves at most once.

## Alternatives considered

- **Client-generated `transfer_id` in the body, unique in a `transfers` table:** a retry hits the unique constraint
  and gets the existing transfer back. No extra table, but it works only for resources with a client-chosen id, so
  top-ups and reversals each need their own version. Detecting "same id, different body" still needs a stored
  fingerprint, and no `transfers` table exists yet.
- **Server-side dedupe by fingerprint within a time window** (same user, same body within N seconds): needs nothing
  from the client, but it rejects real repeated payments, and a retry after the window still posts twice.
- **Keys in Redis:** fast with built-in expiry, but the key and the entry would live in two systems. A crash between
  the database commit and the Redis write loses the key, and the next retry posts again. Redis also doesn't exist in
  the stack until January.
- **No server support; the client checks the history before retrying:** racy (the first request may still be
  running) and pushes ledger correctness onto every client.
